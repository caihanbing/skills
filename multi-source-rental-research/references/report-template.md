# Report template

## Discovery coverage

Before tables, state the target city/location and the discovery ledger: provider, source class (geographic or rental-market), query, entry/result URL, retrieved date, `applicability_status` and basis when not applicable, access state, limitation, and lead count. Report **raw leads**, **manually resolved unique project candidates**, and **potential Offer leads** separately. Describe coverage by source class, not as a provider-count score.

Source absence is a coverage gap, not proof that a project does not exist or has no vacancy.

## Decision modes

Lead with an Offer-centric shortlist. Keep Project context visible, but never let an old or different Offer satisfy a current requirement.

| Project / Offer | Discovery source and lead type | Precise Xiaohongshu evidence / identity match | P0 status | Fixed / variable / unknown monthly cost | Upfront cash | Commute method | Evidence confidence | Decision-critical source concerns | Critical unknowns | Verdict |
|---|---|---|---|---|---|---|---|---|---|---|

Then state rejected Offers and reasons; source IDs/locators, classes, dates, clusters, freshness and conflicts; cost formulae; and viewing/signing actions. Attribute renter experience as experience, not project fact. State that the result is a bounded evidence search.

Scoped due diligence reports only named Projects/Offers unless alternatives were requested.

## Catalog mode only

Use separate residential-community and centralized-long-term-apartment tables. Include discovery source/lead type, discovery link/date/access state, and Xiaohongshu identity-verification status/link/date. For each final project, run one or two identity-specific Xiaohongshu queries; reserve full positive/negative/decision-specific research for a later decision request or a finalist. Apply 3 → 5 → 8 km expansion only to the category still short. At 8 km say `Found N of requested M; shortage M−N`; never invent entries.

A final catalog project without public Xiaohongshu evidence remains reportable only with that absence clearly shown; do not fill the gap with generic location posts. Treat weak Xiaohongshu identity matches as unverified rather than project experience. Do not offer calibration in an ordinary report; mention it only when the user explicitly requests participation.
