# 工作总结与目标

根据当前周期材料撰写季度目标、季度总结和年度总结。正式稿应延续用户既有的中文工作文稿风格，同时确保每一条总结性事实都能回溯到当前材料。

**核心原则：当前材料决定事实，历史材料只决定写法。** 历史范例中的项目、版本、地区、数据源、进度、覆盖率和成果，不能因为“以前写过”就带入新周期。

需要模仿用户历史文风时，先阅读 [references/style-guide.md](references/style-guide.md)。用户本轮新提供的历史范例优先于该内置指南。

## 模式路由

| 模式 | 当前周期材料 | 历史材料 | 正式稿结构 |
| --- | --- | --- | --- |
| 季度目标 | 零散工作任务、明确的周期或范围 | 历史季度目标 | 工作主题 → `目标` → 编号目标 |
| 季度总结 | 本季度周总结、已确认的本季度目标 | 历史季度总结 | 各工作主题的 `目标` 与 `成果`，再加三个总结段落 |
| 年度总结 | 本年度各季度总结；缺失季度需确认 | 历史年度总结 | `个人业绩`、`价值观`、`表现突出的方面`、`需要改进的方面及下一步努力方向`、`总评语` |

如果用户没有明确说明要写季度目标、季度总结还是年度总结，先询问类型。季度总结缺少本季度目标时，先向用户索要或确认目标，再写完整稿；不要从周总结反推未经确认的目标。年度总结必须先具备本年度四个季度的材料；缺少任一季度时，只列出缺失季度并询问是否补充，不能把“暂无材料”写进年度业绩、突出表现或改进方向，也不能先生成部分年度稿。

季度总结必须沿用用户当前目标材料中的一级标题和层级，不得把某个嵌套目标提升为新的一级工作主题，也不得为周报中的额外事项新建目标。若某项成果不完全对应任何目标，直接归入内容最接近的现有目标成果中。

周期标题按用户已有编号习惯处理：如果当前对话已经明确了本季度标题，例如 `2026.03`，用户随后说“下季度”，可沿用同一编号规则推导为 `2026.04`；这不等于推断具体日期。若没有明确的当前周期或编号规则，则使用用户提供的相对周期表述，不自行补充日期。

## 工作流程

1. 识别文稿类型、周期和用户要求的输出范围。
2. 将输入分成“当前周期事实”“当前周期目标”和“历史风格材料”。历史材料默认只用于结构、语气和措辞参考。
3. 季度目标模式下，以每个原始工作项为主句，补充直接隐含的实施任务，例如方案梳理、开发、联调、验证、文档或上线；保留用户的核心对象和动作，不把工作项改写成未经提供的具体接口、算法、系统边界、指标或责任人。输入包含具体子项时，必须把子项全部覆盖到目标中，不能只摘取上位名词。`上线、发布、交付`等强动作只有在原始工作项或当前上下文明确提出时才使用。
4. 季度目标的扩展检查项按任务类型执行：数据源扩展覆盖类型分类、数据源与驱动关系、配置/连接适配和联调验证；驱动管理页覆盖页面与配套接口、查看/上传/升级/替换流程、前后端联调和功能验证；客户端启动优化覆盖耗时分析、mapper/bean及相关资源加载、方案验证和打包验证；DTS静态脱敏覆盖迁移能力整合、任务生命周期、权限校验、联调、验证和上线；License与版本交付覆盖方案、开发、联调、兼容性、上线、部署包/文档和交付问题；部署包优化覆盖无损发布、部署脚本、外部组件对接、命令简化、配置依赖说明和验证流程。
5. 在内部整理目标归属和事实清单：一级标题、目标条目、事项、状态、结果、周期、来源。不要把“目标”当成“成果”。
6. 按同一任务或交付线程合并周报：开发、自测、联调、部署、文档和问题修复等相关动作通常合并为一条成果，不按周报条数逐条罗列。默认让成果条数与目标条数大致对应；一个目标有3—4条任务时，通常整理为4—5条成果即可。
7. 检查是否存在会改变文稿结论的缺口：完成状态冲突、范围不明、周期不明、关键数据缺失、季度材料缺失或前后表述矛盾。
8. 有这类缺口时，只提出简洁的编号问题并暂停写作；不要同时输出猜测性草稿。用户要求“不要追问”也不能绕过事实确认门槛。
9. 信息足够后，按历史格式生成正式稿，并进行事实回溯自检。

只为解决实质性歧义而提问。季度目标缺少量化指标、日期或验收数字时，默认采用保守的定性表达，不自行添加承诺；只有缺失内容会改变目标范围、责任或交付含义时才追问。

## 事实边界与措辞

- 当前周期材料是成果和状态的唯一事实来源。历史材料不能补充当前周期的事实。
- 只在材料明确支持时使用“完成、上线、发布、覆盖、提升、保障”等强结论；“调研、启动、跟进、支撑、协助、开发中、联调中、测试中、待上线、约30%”等状态必须保留其原有强度。
- 不自行补充数字、日期、版本号、客户/地区、数据源、覆盖率、性能指标、因果关系或客户影响。
- 发现未完成、延期、测试不足或依赖未闭环时，如材料明确说明，应如实写入“需要改进的方面及下一步努力方向”和“总评语”。成果中一般只写已经开展的动作和当前进行中的状态，使用“正在推进、进行中、已开展、持续跟进”等中性表达，避免使用“未完成、尚未、仍待”等否定性结论；用户明确要求披露时除外。
- 目标没有对应周报记录，不等于目标未完成。除非当前材料明确说明，或用户确认该目标未完成/需要改进，否则不要把“没有记录”写成缺口、延期或下一步任务；用户明确要求忽略时，直接不写该目标的成果和改进项。
- 可以合并重复周报、压缩同一事项的过程描述，但不能把“处理问题”升级为“问题全部闭环”，也不能把多次跟进升级为多项成果。
- 目标使用面向未来的行动表达；总结使用当前周期已发生的事实表达。不要因为目标写过就声称目标已完成。

## 输出契约

信息已确认完整后，只输出可直接粘贴的正式稿，不附分析、证据表、写作说明或“以下是草稿”等前言。使用用户提供的周期和日期，不自行推断日期。

- **季度目标**：按工作主题归纳零散任务，每个主题使用 `目标` 和编号条目；一级主题优先采用历史中已经形成的正式业务名称，不机械复制“客户端”“私有云”等临时分类。对当前这类任务，优先使用“端云协同客户端的设计和开发”“私有云/混合云版本输出及交付”等历史正式主题名称。每条目标保留原始工作项的核心动作，并按“工作结果 + 直接实施任务 + 验证/交付”展开；输入中的具体子项必须全部体现，不新增未给出的接口、架构、算法、数字、日期或责任人。只有原始工作项明确要求时才写“上线、发布、交付”。
- **季度总结**：原样沿用用户提供的一级标题、目标层级和目标条目，不新增一级工作主题，也不擅自删除用户提供的目标；用户说“忽略某目标”时，默认只是不补写该目标的成果、缺口或改进内容，除非用户明确要求删除目标条目。每个主题的 `目标` 只能来自已确认的季度目标，`成果` 只能来自本季度材料。按任务归并成果，通常使成果条数与目标条数大致对应，相关开发、联调、部署和问题处理合并为一条；目标没有当前证据时不强行补成果，也不自动写入改进段落。随后保留 `表现突出的方面`、`需要改进的方面及下一步努力方向`、`总评语`，其中前两部分各写一段连贯总结，不使用编号列表。若用户确认不需要目标段落，才省略该段落。
- **年度总结**：按历史顺序输出 `个人业绩`、`价值观`、`表现突出的方面`、`需要改进的方面及下一步努力方向`、`总评语`。用户未另行要求时，`价值观`沿用历史固定表述：“认同并践行天翼云的使命、愿景、价值观、精神。”不得据此扩展新的业绩事实。
- 保持中文正式、简洁、客观的语气；优先使用编号列表和用户历史中已经出现的工作术语。

## 输出前自检

逐条检查：

1. 每个成果都能在当前周期材料中找到依据。
2. 没有把历史项目或旧数据源带入本期。
3. 没有把“跟进、协助、测试中、部分完成”改写成“完成、上线或显著提升”。
4. 所有缺失信息、状态冲突和未确认范围都已在写作前询问。
5. 没有把嵌套目标提升为新主题，没有把每周记录机械拆成成果条目。
6. “表现突出的方面”和“需要改进的方面及下一步努力方向”各为一段连贯文字，不是编号列表。
7. 标题、分组、编号和总结段落符合 [references/style-guide.md](references/style-guide.md)。

## 常见误区

| 误区 | 正确处理 |
| --- | --- |
| “历史里有类似项目，可以直接套用” | 只套用结构和文风；当前事实必须重新取证。 |
| “周报里出现了新事项，可以新建一个目标章节” | 保留用户目标的一级层级，将事项归入最接近的现有目标成果。 |
| “每周做了一件事，就列一条成果” | 按任务或交付线程合并开发、自测、联调、部署和问题处理。 |
| “约30%可以润色成基本完成” | 保留原进度和未完成状态。 |
| “把未完成原因直接写进成果更完整” | 成果写当前进行中的动作，缺口和下一步放入改进段落。 |
| “目标没有周报记录，说明目标没完成” | 缺少记录不能证明未完成；未获确认时不写成缺口或下一步任务。 |
| “用户说忽略某目标，就把目标条目删掉” | 默认保留用户提供的目标，只忽略该目标的成果、缺口和改进描述。 |
| “缺一个季度也先写完整年度总结” | 先确认缺失材料或结论范围。 |
| “把没有季度材料写成暂无工作或材料不完整” | 没有材料不等于没有工作；年度总结缺季度时停止写作并询问。 |
| “用户要求直接写，所以不要提问” | 必要的事实确认优先于输出速度。 |
| “目标写得越量化越专业” | 没有来源的数字、日期和指标不应新增。 |
| “工作项已经有了，目标直接重复一句即可” | 保留原始主句，并补齐该工作项直接涉及的实施、联调、验证和交付环节；具体子项不能遗漏。 |
| “实现页面就默认写上线” | 页面开发可展开为接口、流程、联调和验证；只有原始材料明确要求时才写上线。 |
