# 工作总结与目标：内置风格指南

## 使用边界

本文件只保存从用户历史文稿中提炼的结构、语气和少量例句，不是当前周期的事实库。用户本轮提供的历史范例优先于本文件；任何历史例句中的项目名、版本号、地区、数据源、进度和成果都不能直接复用于新总结。

## 文稿结构

### 季度目标

通常以周期标题开头，按工作主题分组。每个主题先写 `目标`，再用编号条目描述计划交付：

```text
DMS产品核心能力建设
目标
1.完成客户端动态加载方案的技术调研、方案设计和核心功能实现。
2.持续优化客户端性能，降低启动时间和资源占用。
```

目标常用“完成、支撑、跟进、调研、完善、持续优化、提升、保障”等动词。没有材料支持时，不补充具体日期、数字、版本或验收口径。

季度目标不应只是把工作项原样抄回。应保留工作项的核心对象和动作，并补充其直接隐含的实施链路，例如方案梳理、功能开发、前后端联调、验证、文档和上线；不要凭空增加具体接口、算法、系统边界、指标或责任人。

工作主题优先沿用历史正式名称：客户端研发类工作使用“端云协同客户端的设计和开发”；私有云、混合云、翼龙1.0、License、部署包和部署文档类工作使用“私有云/混合云版本输出及交付”。只有主题范围明显不同，才重新命名。

例如，`整合DTS迁移能力，上线静态脱敏功能`可以展开为“整合DTS迁移能力，完善静态脱敏任务的创建、预检查、启动、暂停、重启、状态处理及权限校验，完成前后端联调、功能验证和版本上线”；但不应在用户未提供依据时改写成特定的接口架构、服务拆分或数据表设计。

常见工作项的扩展检查项：

- 数据源类型扩展：数据源分类、数据源与驱动对应关系、配置与连接适配、相关功能适配、联调验证。
- 驱动管理页：页面和配套接口、驱动查看/上传/升级/替换流程、前后端联调、功能验证；除非原始任务明确，不写“上线”。
- 客户端启动性能：启动耗时与资源加载分析、mapper/bean及相关资源加载策略、方案验证、打包验证和效果跟踪。
- DTS静态脱敏：迁移能力整合、任务创建/预检查/启动/暂停/重启/状态处理/权限校验、前后端联调、功能验证和上线。
- License与版本交付：方案落地、功能开发、联调、兼容性验证、上线、部署包和文档发布、部署验证及交付问题跟进。
- 部署包优化：无损发布、部署脚本、Kafka/OSS/MySQL等外部组件自动对接、命令简化、配置和依赖说明、验证流程及可维护性提升。

这些是与工作项直接相关的扩展检查项，不是必须机械全部添加的固定清单；当前工作项未涉及的细节不应补入目标。

如果当前对话已经出现 `2026.03` 这类周期编号，用户说“下季度”时沿用同一编号规则写为 `2026.04`；不要额外推断具体日期。没有编号锚点时，保留“下季度”即可。

### 季度总结

历史稿通常保留目标与成果的对应关系，然后补充三个总结段落：

```text
版本和制品包管理
目标
1.进一步完善版本发布流程，持续优化私有云交付流程。
成果
1.跟进相关版本发版工作，整理研发环境流水线并修复问题，优化制品交付流程。

表现突出的方面
在多项并行任务下持续跟进，保障版本发布和交付质量。

需要改进的方面及下一步努力方向
核心功能进度滞后，下一步需集中资源完成开发、联调与兼容性测试。

总评语
本季度完成了既定能力建设和交付支撑工作，但关键功能仍需加强任务聚焦，推动后续工作按计划完成。
```

“成果”使用当前周期的实际记录；“表现突出”应概括已有事实；“需要改进”应承认材料明确的延期、缺口或质量问题，并给出下一步行动。

季度总结的一级标题和目标层级直接沿用用户提供的目标材料。目标条目属于哪个一级标题，就在该标题下整理成果；不要把嵌套目标提升为新的章节。周报中没有独立目标对应的事项，归入最接近的现有目标成果中。

成果按同一任务或交付线程合并，而不是按周拆分。开发、自测、联调、部署、文档和问题修复属于同一交付链路时，通常合并为一条。一般情况下，成果条数与目标条数大致对应；目标有3—4条任务时，成果整理为4—5条即可。

成果中对未完成工作使用“正在推进、进行中、已开展、持续跟进”等中性表达；“未完成、尚未、仍待”等缺口判断放在“需要改进的方面及下一步努力方向”和“总评语”中。

目标没有对应周报记录时，不得据此推断目标未完成、延期或需要下一步整改。只有当前材料明确说明或用户确认的缺口，才能写入改进段落；用户要求忽略的目标，不补写成果或改进事项。

季度总结的目标段落默认原样保留用户提供的目标条目。“忽略某目标”通常只表示不补写该目标的成果、缺口或改进内容；只有用户明确要求删除目标条目时才删除。

### 年度总结

年度总结必须以本年度四个季度材料为事实基础。缺少任一季度时，应先确认是否补充材料或改写为明确限定范围的阶段性总结；不能把“暂无材料”写成年度业绩、突出表现或改进方向，也不能先输出部分年度稿。

历史年度稿的固定顺序是：

```text
个人业绩
...
价值观
认同并践行天翼云的使命、愿景、价值观、精神。
表现突出的方面
...
需要改进的方面及下一步努力方向
...
总评语
...
```

年度“表现突出的方面”应从多个季度的重复事实中提炼长期贡献，例如产品能力建设、私有云/混合云交付、客户问题响应、文档和知识沉淀；不能把单个季度的孤立事项夸大成年贡献。“需要改进”应连接已出现的问题与下一步方向，如进度管理、跨团队协作、测试覆盖、代码健壮性、owner意识和成果沉淀。

“表现突出的方面”和“需要改进的方面及下一步努力方向”通常各写一段连贯文字，不使用编号列表：

```text
表现突出的方面
在多项任务并行的情况下，完成版本交付、环境部署和客户问题处理，持续支撑研发及交付环境稳定运行。

需要改进的方面及下一步努力方向
部署包标准化和发布前质量验证仍在推进，下一步需继续完善部署流程；客户端启动优化效果不明显，需进一步分析启动耗时并持续优化。
```

## 语言特征

- 正式、克制、以工作事实为中心，避免口号化和过度修饰。
- 多使用“完成、支撑、跟进、协助、调研、梳理、改造、联调、测试、上线、交付、保障、优化”等动词。
- 用“启动后端开发，整体进度约30%”“测试中待上线”“除……外，其他任务按期完成”等表达保留真实状态。
- 成果优先写清动作、范围和结果；结果未被材料明确说明时，只写已完成的动作和当前状态。
- 总评语通常先概括主要贡献，再指出未完成事项或改进重点，最后给出下一步方向。

## 精选例句

以下例句用于观察句式，不用于复制其中的事实：

1. 目标句式：`完成技术调研、方案设计、核心功能实现，优先支持主流数据库的动态加载。`
2. 成果句式：`完成第一版与第二版功能的开发自测及前后端联调，扩展了驱动管理、升级、替换能力。`
3. 未完成状态：`启动客户端接入企业版敏感数据保护功能的后端开发，整体进度约30%。`
4. 改进句式：`关键功能仅完成部分开发，未进入联调和测试，下一步需加强任务聚焦，推动功能按计划完成。`
5. 年度价值观固定模板：`认同并践行天翼云的使命、愿景、价值观、精神。`

## 风格自检

生成前后检查：是否使用了用户提供的周期标题或按既有编号规则推导周期；是否保留目标材料的一级标题和层级；是否覆盖每个工作项及其具体子项；是否补充了直接相关的实施、联调、验证和交付任务；是否把未经提出的接口、架构、算法、指标或日期带入目标；是否保留 `目标`、`成果` 和年度固定段落的顺序；是否按任务或交付线程合并成果；是否把旧例句中的事实误当作新事实；是否在成果中使用中性进行时表达；是否将表现和改进内容各写成一段连贯文字。
