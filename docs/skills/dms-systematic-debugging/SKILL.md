# 系统化排查

可独立调用；不要求先启动或加载总流程。

适用于异常行为、测试或构建失败、性能和集成问题。先建立根因证据，再提出修复或修改；错误暴露点不等于根因。简单、稳定复现的问题可直接进行最小定位与验证。

## 定位

1. 读取完整错误、调用栈、警告和原始输入，核对会影响判断的版本、配置、状态与触发条件。简化复现时说明与原场景的差异。
2. 比较最近改动、依赖和环境差异，从坏值或错误状态反向追至来源；只有出现条件变化或新的判别目标才重试已失败的方法。需要时读取 [反向追溯根因](references/root-cause-tracing.md)。
3. 跨组件或异步问题先在边界采集同一次操作的输入、输出和状态变化。高成本采集先用小样本验证关联方式；操作可能已有副作用时核对实际状态。证据不能关联时，先补采集，不拼成因果链。
4. 运行时行为不清楚时，优先采用当前可用且已授权的调试器或诊断手段；跨进程、跨机器或不能调试时使用可关联的日志。查找正常样例，完整比较实现、差异和依赖，不按名称照搬。

## 修复与验证

一次只验证一个具体假设，并预先说明什么结果会支持或排除它。假设不成立时回到定位，不在旧修复上叠加改动。修复根因，保持最小范围，不顺带重构。

纯诊断、只读请求只采证和报告，不改代码或运行会写入环境的操作。已获授权的实现或修复，按适用规则进入 `dms-test-gate`；同样服从宿主强制的调用与权限限制。改代码后编译受影响范围，验证至少覆盖原复现路径和直接受影响的回归，并如实记录快照、命令或操作、结果、限制和结论。单次未复现不能单独证明已修复；测试配置忽略失败时，仍须检查实际失败、错误和跳过统计。

只有根因表明必须实质扩大范围、改变风险或验收，或需要未授权的大规模改动时，才暂停受影响事项并对齐；已授权且独立的工作继续。对高后果数据流，按需读取 [分层校验](references/defense-in-depth.md)；对时序性 flaky 测试，按需读取 [条件轮询](references/condition-based-waiting.md)。

## 同一问题的修复失败

只累计同一问题的实际修复经验证失败；只读取证、预期失败的复现、无关既有失败和环境阻断不计入。每次重试必须带来新证据、修正假设或不同处理。

| 累计失败 | 动作 |
| --- | --- |
| 1 次 | 带新证据重新定位，换一种思路。 |
| 2 次 | 继续换思路，说明困难、已排除项和当前阻断。 |
| 3 次 | 停止该问题的修复并与成员讨论方向；不做第 4 次尝试。 |

暂停只影响该问题。任务内仍有已授权且能区分假设的取证路径时继续；不固定要求重建环境。核对诊断手段、输入和环境变化对新症状的影响，不默认与原故障同因或无关。收尾时逐项区分已证实、已排除、未验证和环境限制；成功样例、机制实验或一次未复现都不能代替原问题的验证。

## 公共契约

- 独立排查 DMS 问题时，按 [DMS 项目依据](../dms-dev/references/dms-project-context.md) 定位本任务的模块、数据/租户边界和适用规范。
- 判断操作范围、只读边界、阶段和交付状态时，读取 [工作流契约](../dms-dev/references/workflow-contract.md)。
- 记录复现、快照、验证和结论时，读取 [任务契约](../dms-dev/references/task-contract.md)。
- 需要处理重试、阻断或中断恢复时，读取 [执行策略](../dms-dev/references/execution-policy.md)。
