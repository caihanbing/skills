# DMS 项目依据导航

本文件供入口、需求澄清、设计检查、规划、执行和调试独立使用。只调查本任务需要的事实与要求，将结论放入已有设计、任务或 `expected_checks`，不新增表单或全项目清单。当前请求、实际生效的项目规则和本次批准决定限定范围；已有结论在相关版本与前提仍成立时复用。

## 从实际入口选择改动位置

先核对当前 checkout、分支、未提交成果及本任务相关的 AGENTS.md。用 [仓库模块概览](../../../../README.md#仓库结构) 找线索，再核对 [根 POM](../../../../pom.xml)、实际目录、启动类及调用点；概览不代替源码，不能顺着旧说明读取仓库根 `scripts/` 或以仓库 CI 推断生产行为。

| 本任务涉及 | 需要查到的事实 | 对设计与验证的影响 |
| --- | --- | --- |
| 应用或共享能力 | 从真实 HTTP/RPC/任务入口沿调用链到改动处，确认 `apps/` 与 `infra/` 职责、DMS/DAS 的实际消费者 | 优先复用现有实现；共享改动覆盖直接受影响消费者，不假设固定四层或每个应用都有 build 模块 |
| 数据读写 | 区分 DMS 自身元数据与用户目标数据库，明确连接、数据归属、事务及读写路径 | 分别说明结构/数据影响、失败结果及必要回退；不能用一侧的数据验证另一侧 |
| SQL 审核、改写或执行 | 顺着实际调用查解析、规则、改写/回滚和执行边界；按需定位 `infra/dms-sqlparser`、`dms-control-rule`、`dms-sql-alter`、`dms-sql-rollback`，确认目标方言 | 明确 SQL 在各边界的输入输出和执行副作用；解析成功不代表改写正确或已安全执行 |
| 权限或租户隔离 | 从实际入口核对身份来源、资源归属、最终查询/写入条件和拒绝后是否终止；共享接口检查调用方与消费者 | 参数带租户标识不等于隔离成立；验收覆盖获准与拒绝路径，按原条件选用安全检查，不自动扩成全量审计 |

查明现有能力、业务期望和未知项分别是什么。源码说明当前如何运行，不能独自证明期望行为、规范豁免或线上状态；个人历史记录只作补充线索，团队必需依据须能在仓库或明确的团队渠道取得。

## 采用适用规范，保留原等级与条件

从 [规约目录](../../../../config/coding-guidelines/README.md) 选择本次相关条款，按原文的【强制】/【推荐】/【参考】及其对象、阶段、触发条件使用，不把推荐升级为强制，也不因检查工具未报错而降低强制要求。

| 依据 | 何时读取 |
| --- | --- |
| [阿里巴巴 Java 开发手册摘要](../../../../config/coding-guidelines/coding-guidelines.md) | 按改动选命名/OOP、集合、并发、异常、SQL、安全或分层等条款；不要求每次通读 |
| [项目自定义规约](../../../../config/coding-guidelines/coding-guidelines-custom.md) | 对照直接涉及的项目补充要求，如 Integer 比较、接口注释和共享修复 |
| [灰度发布规范](../../../../config/coding-guidelines/coding-guidelines-gray-deployment.md) | 实际部署存在新旧版本共存、共享资源或升级/回退影响时，选对应数据库、接口、配置和任务条款 |
| [设计文档组织与归档规范](../../../../docs/code-quality/设计文档组织与归档规范.md) | 设计时确定维护位置及必要拆分，实施时同步现行设计，交付或归档时核对内容、索引和状态；复用已有接口资料并保留必要人工契约 |
| [研发流程必做项](../../../../docs/code-quality/研发流程必做项.md) | 核对当前阶段的设计、测试、审查及交付义务；注意适用产物和试点/强制拦截条件 |
| [团队协作规范](../../../../docs/code-quality/团队协作规范.md)、[审查记录规范](../../../../docs/code-quality/审查记录规范.md) | 准备审查、提测或 MR 资料时读取；文档中流程目标不证明实际 CI/运行配置已经生效 |

检查手段与规范义务分开：当前根 POM 的 Checkstyle 是告警配置，构建成功不证明符合规约；Surefire 忽略失败时仍需读真实失败/错误/跳过明细。Java 工具链与检查配置以本次 POM 和有效项目规则为准。

在 [任务契约](task-contract.md) 的同一 `expected_checks` 中记录来源/版本、原等级/适用条件、检查对象/方法及证据；规则用原章节或条款定位，内容版本用可核对提交或文件指纹。编码风格可人工或静态核对，行为、兼容和安全问题采用能回答该验收问题的方法，不要求每条规范各写单测。

遇到规范与实现或已批准契约冲突，保留双方原文、版本和实际影响，先查是否有有效的团队决定；没有依据时不能自行认定豁免或为符合文本擅自改协议。例如错误码规范与现有 `ServerResponse` 整数协议的差异，只在本任务触及该边界时列为待决，暂停依赖该决定的工作，继续独立已授权事项。

## 只选影响本次验收的运行约束

- **兼容与灰度**：查实际适用部署及发布物料，说明新旧生产者/消费者、请求/响应缺省值、数据迁移和回退的行为。缺省兼容应在输入/转换或业务边界定义，不等于给 POJO 字段直接初始化。无法取得真实配置时标记未验证，不以仓库样例代替线上证据，也不自动获得生产访问或发布授权。
- **性能与资源**：相关任务才查延迟、容量、超时、连接/线程/队列等约束，优先复用已确认目标和有效测量。未知且影响方案的指标先调查或对齐，不自设阈值，不默认压测。
- **可靠性与可观测性**：相关任务才区分业务成功、持久化留痕及通知送达，明确失败、丢失、重复、重启后的预期及必要诊断信息；不从“可追溯”推导完整恢复机制。

关键不确定性尚未解决时，限定调查或获准验证的目标及停止条件，交付结论、证据和限制。接口、数据模型或失败语义在实施中变化时，按 [工作流契约](workflow-contract.md) 同步原设计、任务与验证目标；这些材料服务当前交付，不额外建立规则服务或设计规范。
