# 生成 commit message

> 唯一源：dms-console 仓库 `docs/skills/dms-commit-msg/`。源提交与未提交内容指纹由安装清单记录；使用副本时核对实际路径、包身份和已记录的适配差异。

根据当前 Git 改动，按本仓库规范生成和核对中文 commit message。

参数：`[--base <ref>] [补充说明...]`。使用当前工具提供的文件读取、检索和只读 Git 能力；需要澄清时直接向用户提问。本技能只生成说明，不执行暂存、提交或推送。

**面向的读者**：三个月后接手的同事——他只有仓库和这条 message，没有你现在的上下文（讨论过谁、试了几轮、当前日期、本机数据都拿不到）。他查不到的东西，写进去等于没写。

## 第一步：确定范围

```bash
git status --short
git diff --cached --stat
```

- 有暂存内容 → 只描述**已暂存**部分。
- 无暂存内容 → 描述整个工作区，开头注明"当前无暂存内容，以下基于全部工作区改动"。
- 未跟踪文件（`??`）不在任何 diff 里，易漏：若属本次改动，末尾列出并提醒"尚未 `git add`，直接提交不含这些"。拿不准是否纳入就问。

带 `--base <ref>` 时改为描述 `<ref>...HEAD` 的已提交净变化（覆盖上面的暂存规则；若另有未提交改动，末尾提一句未写入）：

```bash
git diff <ref>...HEAD --stat
git diff <ref>...HEAD
```

不论哪种，"改了又改回去"的净零变化不写进 message。

## 第二步：读懂改动

`--stat` 只用于定位文件，**必须读取实际 diff**，识别主要净变化。变更原因依据代码上下文、关联 issue 或待解决的问题判断；依据不足时询问用户，不编造原因。

## 第三步：写 message

```
类型(模块): 描述
```

**类型**：只用 `feat` / `fix` / `refactor` / `perf` / `docs` / `chore` 六个。仓库历史里有不合规写法，别跟着学。

**模块**：团队看得懂的业务域中文名（如 SQL审核、实例管理），不是 maven 模块名。改的是仓库工程设施（skill、构建脚本、CI）时用仓库既有叫法（如 skills）。跨多模块取主要那个；确属全局改动可省略括号。

**描述**（标题行）：
- 概括主要变更内容，说明变更原因或影响。
- 用团队通用的业务/技术术语；不用内部简称或临时编号（工单号、方案序号、临时代称等）——接手者无从查证其所指，不能替换成可查证名称（类名、表名、业务术语）的一律删去。
- 中文，一行写完，不加句号。
- 一遍要读得懂：同事只读一遍、不回头，读不顺的拆短重写；口吻是工程记录而非复盘随笔（"贴进发版记录像一条事实"即合格）；不写"合规""站得住"这类对规则的评语。

**正文**（可选）：存在两项以上可独立说明的变更时使用正文；只有一项变更时仅写标题，涉及文件数量不影响判断（一次机械重命名涉及多个文件仍属一项变更）。正文使用 `- ` 列表，一条一行一项主要净变化，写明变更对象的可查名称（如 Skill 名称）及新增、调整、删除等实际动作；相关的变更原因可在同一条中简要说明。推断的因果关系应标明为推断；表述完整、清楚优先于省字。

## 第四步：输出前自检

输出前，将提交说明作为未参与讨论的同事理解本次变更的独立说明，核对以下内容及第三步的格式要求：

1. **准确完整**：对照实际 diff，核对每项主要净变化是否已在提交说明中明确表达；再核对每项描述是否有 diff 依据，排除未实施的内容和净零变化。
2. **可查证**：每个词与短语，接手者能确定它指什么吗？像简称的会被查，像普通词的（"那个""上次""几轮"）反而易漏。查不到就换可查证名称，换不出就删。例外：全局可解析的编号（CVE、HTTP 状态码、SQL 错误码、Flyway 序号）；工单号仅当它是补充（划掉整句仍通）才留。
3. **变更原因**：标题是否概括主要变更内容并说明原因或影响；依据不足时补充调查或询问用户，不编造原因。
4. **该拆**：标题要用"并/同时/以及"才说得完，是两笔改动挤在一起的信号——拆开各写。先把标题写到如实覆盖主改动再看需不需要连接词，别靠收窄主题假装通过。

## 参考

```
feat(SQL审核): 新增隐式类型转换检测规则，避免线上性能问题
fix(实例管理): 修复分页查询未过滤已删除实例的问题
refactor(连接池): 简化连接获取逻辑，移除冗余同步
```

不可出现：`update code`、`修复bug`、`添加了新功能`、`一些改动`。

## 输出

message 用代码块包裹。仅在需要说明范围、相关未跟踪文件、拆分建议或缺失的变更原因时附一句必要说明；信息齐全时只给 message。

开发流程交接只提供实际交付范围、验证状态及 Git 状态作为背景；提交说明仍以本 Skill 选定的真实 diff 为准。生成说明不把未验证工作写成通过，不授权暂存、提交、推送或发布。
