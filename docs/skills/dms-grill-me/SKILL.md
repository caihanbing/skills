# 关键决定澄清

可独立调用；不要求先启动或加载总流程。

先按 [工作流契约](../dms-dev/references/workflow-contract.md#授权与阶段) 核对本轮目标依据。仅在继续工作会对目标、业务语义、范围、关键取舍或验收造成实质影响，且既有需求、契约、批准决定或可核实事实无法确定答案时使用。先按 [DMS 项目依据](../dms-dev/references/dms-project-context.md) 查现有入口、能力及相关边界，区分实现事实、业务期望和未知项；事实问题由执行者核实，不转问成员。

清楚的小任务、已有有效方案和已批准决定直接承接。已批准范围内的常规、可逆技术选择自行决定并说明；不要为了凑流程虚构问题、替代方案或审批。

用户尚未明确目标，或只提出工具、功能和做法时，从具体场景了解受影响的人、当前问题和期望结果，结合已核实的现状提出暂定理解，并随用户反馈修正。存在不同解释时，说明各自的结果、范围和取舍，供用户补充或纠正。用户难以回答抽象问题时，用实际案例或前后对照帮助判断；仍不明确时先补关键事实。区分暂定目标与已确认决定，不能仅凭选定工具或实现路径认定目标已明确。

涉及异步通知、后台任务或跨服务投递，且故障处理会改变业务承诺时，先区分业务操作、事件留痕和通知送达各自的保证，再核对允许的丢失/重复、进程重启后是否继续，以及成功指接收还是最终完成。只询问仍未决定且影响实现的取舍；“可追溯”不自动要求可靠送达，失败重试也不自动要求重启恢复或跨实例接管。依据已确认的保证选择持久化、幂等、重试和恢复机制。

需要对齐时，按决定依赖分轮提问：先澄清影响方案方向的目标，再问依赖它的方案细节；每轮聚焦当前最影响方向且已具备前提的事项。根据成员刚提供的信息调整追问，不按固定题单逐项问完。问题要具体；存在待选择的取舍时说明影响、可选项和有依据的推荐，不为开放问题编造选项或答案。未答前不假定会改变后续结论。成员授权代为决定时，在其明确授权范围内采用推荐项并列出所作决定；仍超出授权或缺少必要依据的事项保持待决。

结束时由主会话归纳简短的目标、范围、关键场景与可观察验收条件，使成员能判断哪些变化代表问题得到解决。本轮新形成或实质改变的关键目标由成员修正或确认；已有明确原文和有效决定直接复用。保留已确认决定、仍待决定项及其影响。需求已清楚而技术设计不足时，交主会话按工作流契约补设计，再规划或执行，不继续用访谈代替设计；只读请求保持只读，不因澄清自动进入实现。
